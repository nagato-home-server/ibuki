## Event Driven Fallback Bridge

次に、`--path path-via-hub` による強制選択ではなく、active path failure event から YAML の fallback policy を使って hub を選ぶ入口を追加した。

追加/変更:

- `eventnet_netns_plan` に `--active-path PATH_ID` を追加。
- `eventnet_netns_plan` に `--fail-path PATH_ID` を追加。
- `active_path == fail_path` かつ intent の `fallback.enabled == true` の場合、`fallback.path_id` を選ぶ。
- `controller fallback smoke` を追加。

想定イベント:

```text
active path: path-direct
event: path-direct failed
fallback policy: path-via-hub
selected path: path-via-hub
runtime kind: hub
```

実行例:

```sh
sh scripts/controller fallback smoke samples/linux-vm-netns.yaml
```

設計メモ:

- 通常の priority candidates では `path-direct -> path-via-relay-c -> path-via-hub` の順に評価される。
- 今回の目的は「active direct の障害時に、intent の fallback policy を明示的に使う」ことなので、active path failure event と fallback policy を runtime bridge 側で結びつけた。
- これにより、強制 `--path` ではなく event-driven fallback の形で hub runtime を生成できる。

ローカル検証:

- `vm-build-cc.sh` 成功。
- `vm-generate-netns-runtime.sh samples/linux-vm-netns.yaml --active-path path-direct --fail-path path-direct` で `path-via-hub` が選ばれることを確認した。
- reason は `active path path-direct failed; using fallback path-via-hub`。
- `selected-path.txt` に `runtime_kind: hub` と hub の 2 segments が出力されることを確認した。

VM 実行結果:

- `controller fallback smoke samples/linux-vm-netns.yaml` が成功した。
- 初期状態では controller が `path-direct` / `runtime_kind: direct` を選び、direct IPsec smoke が成功した。
- `event: active direct path failed` の後、controller runtime bridge が `path-via-hub` / `runtime_kind: hub` を選んだ。
- reason は `active path path-direct failed; using fallback path-via-hub`。
- fallback 後、`tun-a-hub` と `tun-hub-b` の IKE/CHILD SA が確立した。
- `site-a -> hub-1 -> site-b` の ping は `3 packets transmitted, 3 received, 0% packet loss`。
- ESP out packet counter は `site-a/tun-a-hub: 0 -> 3`、`hub-1/tun-hub-b: 0 -> 3`。
- 最終的に `Controller fallback smoke passed: direct failure event selected and validated hub fallback.` を確認した。

この時点で、`direct path failure event -> YAML fallback policy -> hub runtime generation -> hub IPsec execution -> traffic validation` が通った。

## Recovery Bridge

fallback 成功後、次に `direct failed -> hub fallback -> direct recovered -> direct return` の recovery smoke を追加した。

追加 script:

- `controller recovery smoke`

flow:

```text
phase 1:
  normal priority selection
  selected path: path-direct
  runtime kind: direct

phase 2:
  event: path-direct failed
  fallback policy: path-via-hub
  selected path: path-via-hub
  runtime kind: hub

phase 3:
  event cleared / direct recovered
  normal priority selection
  selected path: path-direct
  runtime kind: direct
```

実行例:

```sh
sh scripts/controller recovery smoke samples/linux-vm-netns.yaml
```

この smoke は各 phase で runtime script を生成し、実際に direct / hub / direct の IPsec smoke を順に通す。

ローカル検証:

- `controller recovery smoke` の shell syntax check 成功。
- `--active-path path-via-hub` かつ failure event なしの場合、通常 priority selection に戻り `path-direct` / `runtime_kind: direct` が生成されることを確認した。

VM 実行結果:

- `controller recovery smoke samples/linux-vm-netns.yaml` が成功した。
- phase 1 で controller が `path-direct` / `runtime_kind: direct` を選び、direct IPsec smoke が成功した。
- phase 2 で `path-direct` failure event から `path-via-hub` / `runtime_kind: hub` が選ばれ、hub IPsec smoke が成功した。
- phase 3 で failure event が消えた状態として通常 priority selection に戻し、再び `path-direct` / `runtime_kind: direct` が選ばれた。
- recovery 後の direct IPsec smoke でも `3 packets transmitted, 3 received, 0% packet loss` と ESP counter 増加を確認した。
- 最終的に `Controller recovery smoke passed: direct -> hub fallback -> direct recovery all validated.` を確認した。

これで、`normal direct -> direct failure -> hub fallback -> direct recovery -> normal direct` の一連の制御ループが VM 上で実 traffic 付きで通った。
