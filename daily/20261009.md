# Daily 20261009

## 実施内容と設計方針

- VMware VM に SSH 接続し、VPP AF_PACKET が ARP 要求を受信して応答を生成する一方、client namespace に応答が届かない問題を再検証した。
- Linux 側の veth オフロード無効化、AF_PACKET v2、qdisc bypass 無効化だけでは先行試験で解消しなかった。
- VPP host-interface 作成時に `cksum-gso-disable` を指定すると、動的 ARP と gateway ping が回復した。qdisc bypass 無効化を併用しない状態でも 3/3 ping が成功した。
- LAN、Linux underlay 接続、VPP 間リンクの全作成箇所へ同設定を適用した。不要になった client の固定 neighbor 登録と MAC 読込を削除し、動的 ARP 自体を試験できる構成にした。
- Linux 7.0.0-34 / VPP 26.06 の実機で、Hub 構成の両 gateway ping が各 2/2、client-a → client-b が 3/3、逆方向も 3/3 成功した。
- Hub の平均 RTT は順方向 26.038 ms、逆方向 70.181 ms。少数の機能確認標本なので、性能評価の代表値としては扱わない。
- 続いて Direct 構成へリンクを再作成し、両 gateway ping 各 2/2、双方向 LAN ping 各 3/3、損失 0% を確認した。LAN 平均 RTT は順方向 31.151 ms、逆方向 34.035 ms。再作成後も固定 neighbor なしで疎通した。
- シェル構文確認と `git diff --check` が成功した。C コードを変更していないため、この修正ではフルビルドを行わない。

## 難しかった点・停滞した点

- VPP の TX カウンタと送信トレースが進むため、送信完了と誤認しやすかった。client 側の受信カウンタ・ARP 状態・ping を合わせて確認する必要があった。
- Linux 側の `ethtool` 設定だけでは VPP の PACKET socket 用オフロード設定を無効化できなかった。
- 本試験はオフロード設定との互換性問題を特定したもので、VPP または Linux の内部不具合箇所まで確定したものではない。

## 検証範囲

- オフロードを無効化した設定を、以後の性能測定条件に明記する。

- GRE の試験成功は未確認。VM 復旧後に、双方向 client 疎通と ESP 送受信シーケンス進行を確認する必要がある。

## VM 復旧後に見つかった問題と修正

- 古い `eventnet_netns_plan` バイナリが旧 LAN アドレスを使った計画を生成していた。VM でビルドし、C unit test 成功を確認した。
- 生成スクリプトの VPP CLI 呼出を `"$@"` で引数を渡す形へ統一した。
- Direct charon 起動処理が namespace 内の全プロセスへ停止シグナルを送っていたため、対象を charon のみに限定した。同居する VPP を停止しない。
- 現在の client LAN と一致しない `172.16.*` 経由のローカル LAN 経路を削除した。VPP の connected route で client に戻す。
- 2 vCPU に system VPP と3つの namespace VPPが同居し、初回 ARP タイムアウトと数秒の RTT が発生した。再起動待ちを延長し、試験用 VPP に1msの poll sleep を設定した。
- IPsec 統合では平文の VPP 間 transit を作成せず、2つの endpoint VPP から TAP / XFRM に渡す `ipsec` topology mode を追加した。GRE 試験は同モードで TAP を省略し、生成計画が GRE を構築する。
- VPPを保持してDirect SAを再確立した手動試験では、client通信でESPのoutが6 packets、inが5 packetsまで進んだ。ただし往路pingに1パケット損失があり、この時点では試験完了としなかった。
- DirectからHubへの再適用で、既存tap0の同一IP登録をVPPが拒否した。既存アドレスを削除してから登録する形に修正した。
- 起動直後のARP解決で初回パケットが欠落するため、測定ping前のneighbor warm-upを明示的に追加した。warm-upの出力もログに残し、起動直後の損失を隠さず通常の疎通試験と分離する。

## IPsec 統合の最終結果

- `MODE=both` の Controller 統合 runtime が終了コード0で完走した。Directを選択した後、Direct failureイベントを与えて `path-via-hub` を選択し、生成された経路を実反映した。
- warm-up 後の client-a → client-b / 逆方向は、Direct・Hub の全4試験で各3/3、損失0%。平均RTTはDirectが29.130 / 37.600 ms、Hubが18.051 / 20.172 ms。3標本の機能確認であり性能比較とは扱わない。
- warm-up の初回往路1パケットは両モードとも損失した。起動直後の無損失切替を達成した結果ではない。
- Hub試験後の実SAは全ノードでESTABLISHED / INSTALLED。site-aのESP out 11 / in 10、Hubの両CHILD_SAで10〜11 packets、site-bもESP out 10 / in 11を確認した。IPsec単体smokeの3 packetsを超えてclient通信が通ったことを確認した。
- 証跡: `out/revalidation-20261009/integrated-confirmed.log`、`hub-sas.log`。途中失敗は同ディレクトリの `integrated.log`、`integrated-latest.log`、`integrated-retry.log`、`integrated-final.log` に残した。
