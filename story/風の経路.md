# 風の経路

午前二時十三分、拠点Aの監視画面から、ひとつの赤い点が消えた。

「Direct Path、応答なし」

夜勤のミナは、画面の数字を二度確認した。回線そのものが落ちたのか、それとも、暗号化されたトンネルの片側だけが沈黙したのか。以前のシステムなら、担当者が複数の端末を開き、設定ファイルとログを一つずつ照合しなければならなかった。

しかし、その夜、画面の中央にIbukiの記録が現れた。

```text
TARGET: path-via-hub
REASON: Direct Path failed health validation
ACTION: Prepare fallback tunnel
```

Ibukiは、まず拠点Aとハブの間にあるIPsecの状態を確認した。IKEの認証、CHILD_SA、暗号化ポリシー。strongSwanが報告した状態は正常だった。次に、VPPへ問い合わせる。GREインターフェースは存在し、FIBにも必要な経路が残っている。

それでも、目的地への検証パケットは返ってこなかった。

「Directの先だけが死んでいる。ハブ経由なら通る可能性がある」

ミナがそう呟くと、Ibukiは新しいPathの準備を始めた。

VPPにはGRE over IPsecの経路を用意させる。GREはIPパケットを仮想的なL3リンクへ収容し、その外側をstrongSwanのIPsecが保護する。Ethernetフレームを拠点間へ延ばす仕組みではない。各拠点のLANは、それぞれの場所で終端し、必要なIP prefixだけが経路として運ばれる。

その間、FRRoutingはまだ何も決めなかった。経路交換と収束を担当するのはFRRoutingだが、どのPathを採用するかを決めるのはIbukiである。役割を混ぜないことが、切替の理由を明確にする。

「Prepare complete」

次にValidate。IPsec SAは確立している。GREインターフェースはup。VPPのFIBには、目的地`10.10.2.0/24`への経路が登録されている。検証パケットがハブを通り、拠点Bから応答が戻った。

Ibukiは、まだDirect Pathを削除しなかった。新しい経路が使えると分かってから、初めてCommitを実行する。

VPPの経路が切り替わり、画面の赤い点が黄色へ、そして緑へ変わった。

```text
PREPARE: tunnel and GRE interface ready
VALIDATE: IPsec SA, FIB, reachability passed
COMMIT: path-via-hub selected
POST VALIDATION: passed
```

ミナはログを見て、切替の理由を読み返した。単に「別の経路へ変更した」とは書かれていない。どの経路が失敗し、何を準備し、どの検証を通過し、なぜ新しい経路が選ばれたのかが残っている。

午前二時二十七分、Direct Pathが復旧した。

今度は逆向きの切替だった。Ibukiは回復した経路をすぐには選ばず、Telemetryの値が安定するまで待った。安定を確認すると、FRRoutingから得られた経路情報とVPPのFIBを照合し、Direct Pathへ戻した。切替後の検証に失敗した場合は、直前のStable PathへRollbackする計画も準備されていた。

朝、ミナは引き継ぎ欄に一行だけ書いた。

「経路は壊れた。しかし、判断と復旧は壊れなかった」

その下で、Ibukiは次の風を待っていた。
