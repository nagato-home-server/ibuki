# Ibuki 設計文章の不足点整理

作成日: 2026-08-18

対象文書:

- 添付文書: `標準Tunnelの抽象化と状態遷移制御に基づく イベント駆動型ネットワーク制御基盤「Ibuki」の設計`
- ローカル文書: `実装方針.md`

## 1. 全体所感

現在の文章は、Ibukiが何を目指す研究・実装であるかをかなり明確に説明できている。
特に、次の二点は軸として強い。

- 標準Tunnelを共通制御リソースとして抽象化すること
- Path変更を単なる設定変更ではなく、状態を持つTransitionとして扱うこと

また、既存OSSを置き換えるのではなく、strongSwan、VPP、FRRなどの上位に制御層を置くという立ち位置も明確である。
これは未踏向けの説明としても良い。
「新しいVPNを作る」のではなく、「既存の標準技術を安全に組み合わせて動かす制御基盤を作る」という方向性が読み取れる。

一方で、現時点の文章には、提出・発表・第三者レビューに向けて補強した方がよい点が残っている。
不足点は、大きく分けると次の五種類である。

- 主張に対して、まだ実験結果が足りない点
- 設計概念は書かれているが、図や表として見えにくい点
- 実装済み範囲と将来構想の境界が一部曖昧な点
- 既存技術との差分をもう一段強く説明すべき点
- セキュリティ、運用、失敗時挙動の記述がまだ薄い点

## 2. 最優先で補強すべき点

## 2.1 「どこまで実装済みか」を冒頭で明確にする

本文後半では、実装済み範囲と未実装範囲が整理されている。
しかし、要旨や序章だけを読むと、Ibuki全体がすでにdaemon、multi-domain、Graceful Transition、Flow Preserveまで含めて実装済みであるようにも読める可能性がある。

未踏提出では、構想と実装の両方を書くこと自体は問題ない。
ただし、実装済み部分と研究構想部分の線引きは早い段階で明示した方が安全である。

追加したい説明:

- 現時点のPrototypeはC言語によるController coreである
- YAMLからPath/Intentを読み込み、Path Selectionを行う
- strongSwanとVPPに対するruntime plan生成とLinux VM上でのsmoke testまでは確認済み
- eventnetd daemon化、Observed State recovery、multi-domain federation、Flow Preserveは今後の実装対象である

入れる場所:

- 要旨の末尾
- 1章の最後
- 20章または21章の冒頭

## 2.2 実装済み結果と将来構想の言葉を分ける

現在の文章では、「想定する」「必要である」「実装した」「確認した」が混在している。
読者は、どれが現時点の成果で、どれが今後の設計なのかを常に追う必要がある。

改善案:

- 実装済み: 「実装した」「確認した」「passした」
- 部分実装: 「生成できる」「初期的に確認した」「partialである」
- 未実装: 「設計対象である」「今後実装する」「現時点では未実装である」

特に注意すべき項目:

- Graceful Transition
- Flow Preserve
- Rollback executor
- Reconciliation Runtime
- Control Plane障害時のActive Path維持
- Controller再起動後のObserved State recovery
- Multi-domain Transition Proposal

## 2.4 図が不足している

現在の文章は概念説明が文章中心である。
Ibukiのような制御基盤は、図があると理解がかなり速くなる。

最低限ほしい図:

1. 全体アーキテクチャ図
2. Resource Model図
3. Path Transition状態遷移図
4. Direct / Hub / Relay Pathの構成図
5. Controller-generated planがstrongSwan/VPPへ反映される流れ

特に必要な図:

- Operator / YAML / Intent
- Ibuki Controller
- Path Selection Engine
- Transition Engine
- Adapter Layer
- strongSwan / VPP / FRR
- Observed State / Applied State / Desired State

図がないと、「結局何を作ったのか」が読み手の頭の中で組み立てる負担になる。
未踏の提出・発表では、図を先に見せて、そのあと文章で補足する方が伝わりやすい。

## 2.5 既存技術との差分を表で強める

ONOS、Kubernetes、flexiWANとの比較は書かれている。
ただし、現状では文章による比較が中心であり、読者が差分を一目で把握しにくい。

追加したい比較軸:

| 比較軸 | Ibuki | ONOS | Kubernetes | flexiWAN |
| --- | --- | --- | --- | --- |
| 主対象 | Tunnel/Path Transition | Network Intent/SDN | Workload desired state | SD-WAN運用 |
| 既存IPsec/VPPの再利用 | 中核方針 | 直接の主対象ではない | 主対象ではない | 製品構成に依存 |
| Path変更の中間状態 | 明示的に扱う | 抽象度が異なる | Pod等の状態管理中心 | 実装依存 |
| Flow Preserve戦略 | 設計対象 | 主対象ではない | 主対象ではない | 製品機能として存在し得る |
| Explain Log | 設計対象・一部実装 | intent可視化はある | events/logs中心 | 運用画面中心 |
| OSS組合せ研究基盤 | 目標 | SDN基盤 | 汎用制御基盤 | SD-WAN製品寄り |

この表を入れると、「既存OSSを寄せ集めただけではない」ことを説明しやすくなる。

## 3. 技術的に不足している説明

## 3.1 Resource Modelの制約条件が不足している

Node、Tunnel、Segment、Path、Candidate Pathの説明はある。
しかし、各リソースの制約条件がまだ弱い。

追加したい制約:

- Segmentは必ず一つのTunnelを参照するのか
- 一つのPathは複数Segmentを持てるが、Segment順序はどう表すのか
- Waypointを持つPathでloopを許すのか
- Tunnelのlocal/remote endpointとSegmentのfrom/to nodeが矛盾した場合どうするのか
- route destination prefixとtraffic selectorは常に一致するのか
- Pathが利用可能と判断されるために必要な最小条件は何か
- Candidate Pathから除外される条件は何か

これらは、YAML validatorや将来のAPI設計にも関わる。
「何を正しい設定とみなすか」が明確になると、実装の信頼性も説明しやすい。

## 3.2 Transition Stateの状態遷移表が不足している

状態名は書かれているが、どのイベントでどこへ遷移するかが表になっていない。

追加したい表:

| 現在状態 | イベント | 次状態 | 失敗時 |
| --- | --- | --- | --- |
| Proposed | target path accepted | Preparing | Failed |
| Preparing | tunnel prepared | Validating | Failed or RollingBack |
| Validating | validation passed | Ready | RollingBack |
| Ready | commit requested | Committing | RollingBack |
| Committing | forwarding changed | Verifying | RollingBack |
| Verifying | traffic verified | Completed | RollingBack |
| RollingBack | rollback succeeded | Completed | Failed |

この表があると、Path Transitionを「第一級の制御対象」とする主張がかなり強くなる。

## 3.3 Strategyごとの差分がまだ抽象的

Immediate、Graceful、Flow Preserveの説明はあるが、具体的にどの操作順序が違うのかをもう少し書いた方がよい。

追加したい比較:

| Strategy | 旧Path | 新Path | Flow単位制御 | 期待効果 | 実装状況 |
| --- | --- | --- | --- | --- | --- |
| Immediate | すぐ切替 | すぐ利用 | しない | 高速切替 | 初期実装相当 |
| Graceful | 短時間維持 | 検証後に利用 | しない | 失敗時復旧しやすい | 未実装 |
| Flow Preserve | 既存Flowを維持 | 新規Flowから利用 | する | session continuity | 未実装 |

## 3.4 Reconciliationの具体化が不足している

Reconciliationの必要性は書かれているが、実際に何を比較するのかが不足している。

追加したい要素:

- Desired State: YAML/Intentから導かれる目標Path
- Planned State: Controllerが生成したplan
- Applied State: Controllerが適用したと記録している状態
- Observed State: strongSwan/VPP/FRRから取得した実状態
- Drift: Applied StateとObserved Stateの差分

追加したい例:

- swanctl上ではSAが消えているが、ControllerはActive Pathだと思っている
- VPP routeが外部操作で削除された
- Controller再起動でApplied Stateを失った
- Hub側は切替済みだがsite-a側は旧Pathのまま

## 3.5 Security Modelが不足している

IbukiはIPsecや制御APIを扱うため、セキュリティ上の前提を明記した方がよい。

不足している観点:

- VICI socketへのアクセス権限
- swanctl credentialやPSKの管理
- 生成されたapply scriptの権限
- Controllerがroot権限で動く範囲
- YAML入力の信頼境界
- Command injection対策
- multi-domain control channelの認証
- Decision Logに秘密情報を出さないこと

現時点では、Prototypeなので完全な対策は不要でもよい。
ただし、「未踏提出時点ではどこまで安全に扱うか」を明記しておくと安心感が出る。

## 4. 評価面で不足している点

## 4.1 定量評価がまだsmoke test中心である

現在の評価は、実際に動いたことを示すには十分である。
一方で、研究・提案として説得力を出すには、定量評価を追加した方がよい。

追加したい測定:

- 切替中のpacket loss数
- 最大通信断時間
- ping RTTの変化
- TCP sessionが維持されるか
- packet reorderingの有無
- fallback plan生成時間の平均、中央値、最大、標準偏差
- integrated runtimeの工程別時間
- CPU使用率、memory使用量

特に重要:

- integrated-directとintegrated-fallbackの時間を、工程別に分解すること

現在は、統合runtime全体で51,944 ms / 75,599 msとなっている。
この値だけだと、どこに時間がかかっているのかわからない。

分解したい工程:

- YAML parse
- Path Selection
- runtime plan生成
- IPsec config生成
- charon起動
- swanctl load
- CHILD SA initiate
- ESP counter確認
- VPP host-interface setup
- VPP route apply
- ping verification

## 4.2 比較対象が不足している

Ibukiを使った場合の有効性を示すには、比較対象が必要である。

比較候補:

- 手書きshell scriptでDirect/Hubを切り替える場合
- strongSwanのみでIPsecを管理する場合
- VPP routeだけを手動変更する場合
- FRR/BGP metric変更で経路制御する場合

比較軸:

- 切替手順数
- 設定ファイル数
- 失敗時に戻せるか
- 判断理由をログとして説明できるか
- Direct/Hub/Relayのような複数Pathを同一モデルで扱えるか

## 4.3 GracefulとFlow Preserveが未評価である

本文ではImmediate、Graceful、Flow Preserveが重要なStrategyとして出てくる。
しかし、現時点で実装・評価できているのはImmediate相当である。

提出時に必要な整理:

- 未踏提出までにGracefulを実装するか
- Flow Preserveは設計のみとして残すか
- もしFlow Preserveを未実装にするなら、なぜ未踏期間内では対象外にするのか

おすすめ:

- Gracefulは簡易版を実装する
- Flow Preserveは将来課題として明示する

Graceful簡易版の例:

- 新Pathを先に確立
- 新Pathで検証ping
- 旧Pathを一定秒数維持
- VPP routeを切替
- 切替後検証
- 失敗時は旧Pathへ戻す

## 4.4 Rollback評価が不足している

Rollbackは設計上かなり重要である。
現時点ではfallback plan生成は確認されているが、runtime rollback executorは未実装である。

追加したい評価:

- VPP route投入に失敗した場合に旧routeへ戻せるか
- IPsec SA確立に失敗した場合に旧Pathを維持できるか
- Hub側だけ成功しsite-a側が失敗した場合にどう収束するか
- Rollbackに要する時間
- Rollback成功率

## 4.5 Control Plane障害とrestart recoveryが未評価である

Control Plane障害時のActive Path維持は、ネットワーク制御基盤として重要である。
現在はgenerated-plan型なので、daemonが死んだ場合の挙動を評価できない。

将来必要な実装:

- eventnetd daemon
- state store
- observed state collector
- reconciliation loop
- restart recovery test

評価例:

- Direct Path適用後にeventnetdをkillする
- trafficが維持されるか確認する
- eventnetd再起動後にObserved StateからActive Pathを復元する
- Controllerの内部状態と実network状態が一致するか確認する

## 6.2 要旨がやや長い

要旨はよく書けているが、やや長い。
提出先の文字数制限がある場合、少し圧縮した方がよい。

残すべき要素:

## 6.3 「標準Tunnel」という語の定義を早める

タイトルにもある「標準Tunnel」が、読む人によって解釈が分かれる可能性がある。

定義案:

本稿でいう標準Tunnelとは、独自プロトコルではなく、IPsec/IKEv2や既存のルーティング・転送機構により形成される、相互運用可能な拠点間通信路を指す。

この定義を序章または研究目的の前に入れるとよい。

## 8. 文章に追記するとよい短い補足案

以下は、そのまま本文へ移植しやすい補足文である。

### 8.1 実装範囲の補足

現時点のPrototypeは、Ibuki全体構想のうち、YAMLに基づくPath定義、Intentに対するPath Selection、障害イベントに基づくFallback判断、Explain出力、strongSwanおよびVPPに対するruntime plan生成、Linux VM上でのDirect/Hub統合smoke testを対象としている。一方で、daemon化、Observed Stateに基づくReconciliation、Graceful/Flow Preserve Transition、複数Domain Controller間協調は今後の実装対象である。

### 8.2 評価結果の補足

評価Scriptにより、Scenario Harness、Fallback plan生成、Explain JSONL、Backend reuse、IPsec/VPP統合runtimeを確認した。Direct Pathを用いる統合runtimeおよびDirect障害時のHub Fallback統合runtimeはいずれもpassした。ただし、ここで測定された時間は、各確認処理を含むsmoke test全体の実行時間であり、実運用上の通信断時間そのものではない。

### 8.3 未実装範囲の補足

現時点でpartialまたはskipとなっている評価項目は、Ibukiの設計が不要であることを示すものではなく、むしろ今後の実装対象を明確にするものである。特に、Rollback executor、Observed State recovery、Control Plane障害時のActive Path維持、Multi-domain Transition Proposalは、Prototypeを実運用に近づけるうえで重要な課題である。

## 9. まとめ

現在の文章は、Ibukiの研究テーマと初期実装の方向性を説明する骨格としては十分に強い。
特に、Tunnel抽象化とPath Transition状態モデルという二つの軸は明確であり、未踏提出向けの中心主張として使える。

不足しているのは、主に「読者が一目で理解できる形」への変換である。
図、表、実装範囲の明確化、評価結果の整理を追加すれば、かなり読みやすくなる。

次に実装面で伸ばすなら、Graceful簡易版またはRollback executorが最も効果的である。
文章面で伸ばすなら、Architecture図、Transition状態遷移表、評価結果表、既存技術比較表を優先するのがよい。
